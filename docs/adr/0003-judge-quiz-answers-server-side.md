## 文脈

git操作クイズは4択で出題し、正誤判定を返す。素直に実装すると
「質問一覧APIに選択肢と正解インデックスを両方含め、フロントで比較して判定する」
形になりやすい。しかしこの形では、質問取得のレスポンスJSONを見るだけで
正解が分かってしまう（ブラウザの開発者ツールのNetworkタブで丸見えになる）。
クイズとして出題する以上、正解はクライアントに事前に渡してはならない制約がある。

一方で判定をどこでやるかはAPIの形を決める。フロントだけで判定するのか、
サーバーに答えを送って判定してもらうのかで、エンドポイントの数も
DTOの形も変わる。あとから変えると `frontend/src/features/quiz` と
`backend/.../quiz` の両方の契約を壊すため、最初に決めておく。

## 決定

質問一覧取得と正誤判定を別エンドポイントに分け、判定はサーバー側で行う。

- `GET /api/quiz/questions` は `QuizQuestionDto(id, question, choices)` のみを返す。
  正解インデックスはレスポンスに含めない。
- `POST /api/quiz/questions/{id}/answer` に選択したインデックスを送り、
  サーバーが正解と照合して `AnswerResultDto(correct, correctIndex, explanation)` を返す。

## 結果

### よくなること

- レスポンスJSONのどこにも正解が現れないので、クイズとして成立する。
- 正誤判定ロジックが1箇所（`QuizService`）に閉じる。フロントは比較ロジックを持たない。

### 悪くなること

- 1問答えるごとにAPI呼び出しが発生する（オフラインでは動かない）。
- DTOが `QuizQuestionDto`（出題用）と `AnswerResultDto`（判定結果用）の2種類に分かれ、
  保守対象が増える。

## 検討した代替案

- **質問一覧に正解インデックスも含め、フロントで比較して判定する** — 実装は単純で
  API呼び出しも1回で済むが、レスポンスJSONに正解がそのまま載るため不採用。
