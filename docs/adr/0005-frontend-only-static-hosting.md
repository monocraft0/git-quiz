## 文脈

ADR 0004 では、gitの挙動をフロントのシミュレータで再現しつつ、ミッションの取得と
正誤判定だけを Spring Boot + PostgreSQL に置いていた。しかしこのアプリで
サーバーが担う仕事は「ミッションを返す」「状態を目標条件と照合する」だけで、
ユーザー認証も永続化すべきユーザーデータも無い。

一方で `npm run dev` 以外の手段（GitHub Pages）で誰でも動作確認できるようにしたい。
GitHub Pages は静的ファイルしか配信できないため、BE が要る構成では動かない。

## 決定

BE（Spring Boot）・DB（PostgreSQL / Flyway）・`infra/` を削除し、フロントエンドのみの
構成にする。ミッションの定義（初期化コマンド・目標・模範解答・解説）と判定は
`frontend/src/features/missions` に同梱し、`.github/workflows/pages.yml` で
main への push ごとに GitHub Pages へデプロイする。

## 結果

### よくなること

- サーバー・DB・Docker が不要になり、`npm install && npm run dev` だけで動く。
- 誰でもURLを開くだけで試せる。運用コストはゼロ。
- 判定が同期関数になり、通信エラーやローディング状態の分岐が消えた。

### 悪くなること

- 模範解答・解説・判定条件がJSに含まれるため、開発者ツールを見れば答えが分かる。
  ADR 0003 の「正解を判定前にクライアントへ渡さない」方針は放棄する（0003 は 0004 で
  置き換え済み）。学習用でスコアに価値が無いため受け入れる。
- 問題の追加・修正は再デプロイが要る（DBの行を足すだけでは済まない）。
- 進捗やスコアの保存先が無い。必要になったら localStorage を検討する。
- CLAUDE.md のスタック（Kotlin / PostgreSQL / DynamoDB）と設計原則の一部は
  このアプリでは適用しない。

## 検討した代替案

- **BE を残して静的版を追加で作る** — 両方を保守する必要があり、同じ判定ロジックを
  TypeScript と Kotlin に二重に持つことになるため不採用。
- **無料のBaaS（Firebase 等）に判定を置く** — 答えを隠せるが、外部サービスへの依存と
  アカウント管理が増える。学習用クイズには過剰なため不採用。
