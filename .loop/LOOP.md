# LOOP.md — このリポジトリのループ規約

ループエンジニアリングの永続状態はこのディレクトリに置く。
モデルの文脈はリセットされるが、`.loop/` はリポジトリに残る。**ここが唯一の真実**。

| ファイル | 役割 |
| --- | --- |
| `LOOP.md` | ループの規約。完了条件・差し戻し上限・禁止事項（このファイル） |
| `backlog.md` | 未着手タスク。ループは**上から1件**取る |
| `done.md` | 完了ログ。追記のみ、書き換えない |

`.loop/` は **gitignore しない**。ループが何をしたかを追える状態を保つため。

判断の記録（ADR）だけは `.loop/` の外、`docs/adr/` に置く。理由は「設計判断の記録（ADR）」。

## 1周の定義

1周 = バックログ1件を、完了条件を満たすところまで持っていくこと。

```
前提: base ブランチがクリーン（未コミットの変更が無い）
  ↓
backlog.md の先頭を1件取る
  ↓
ブランチ loop/<slug> を切る
  ↓
分解（opus。スライスと完了の形を決める。**テストリストを作る**）
  ↓
実装（sub-agents に委譲。sonnet / 機械的なものは haiku）
  ├ 赤: テストを書き、落ちるのを見て、テストだけをコミットする
  ├ 緑: 赤を消す最小限の実装をコミットする
  └ リファクタ: 緑を保ったまま整える（テストリストが尽きるまで繰り返す）
  ↓
ADR（設計判断を含む周だけ。opus が枝の上に書く）
  ↓
機械ゲート: make test && make build
  ├ 赤 → 実装に差し戻し（最大3回）
  └ 緑 ↓
残りを枝へコミット（赤/緑のコミットは実装中に積まれている。レビュー中に落ちても失わないため）
  ↓
verifier: code-reviewer エージェント（試験はリポジトリの複製の上で行う）
  ├ FAIL → 実装に差し戻し（最大3回。ただしADRのBlockerは差し戻さず opus が自分で書く）
  └ PASS ↓
出力ゲート: 成果物を .loop/artifacts/<slug>/ に出して**実際に見る**
  ├ 完了条件の観測条件を満たさない → 実装に差し戻し
  └ 満たす ↓
実装をコミット → base に戻る → merge --no-ff
  ↓
base 上で backlog.md から削除 → done.md に追記 → コミット
```

## ブランチ運用

**base ブランチ**（ループを始めたブランチ。通常 `main`）が積み上がる幹。
`loop/<slug>` は1周ぶんの作業を切り出した枝で、レビューの単位。

- 完了した枝は **base に `--no-ff` でマージする**。マージしないと
  次の周が前の周の成果を見られず、依存するタスクが積めない。
- 枝は**消さずに残す**。あとから1周ぶんの差分だけを読み返せるようにするため。
- `.loop/` の更新（backlog削除・done追記）は**枝ではなく base 上でコミット**する。
  枝に置くと、blocked時に枝ごと捨てた瞬間に記録も消える。
- **push も PR も作らない**。base はローカルに閉じている。

### 前提：作業ツリーがクリーンであること

ループは blocked 時に `git reset --hard` と `git clean -fd` を使う。
**未コミットの変更が残っていると巻き込んで消す**。
1周を始める前に必ず `git status` を確認し、汚れていたら着手しない。

## 完了条件

次の**3つすべて**を満たすまで、そのタスクは完了ではない。

1. **機械ゲート** — `make test && make build` が緑
2. **レビュー合否** — `code-reviewer` エージェントが `PASS` を返す（Blocker ゼロ）
3. **出力ゲート** — 成果物を実際に見て、タスクの `見て確かめること:` を満たしている

タスク側で `完了条件:` を書いた場合は、上の3つに**追加**される（置き換えではない）。

**着手条件が1つある**。実装スライスは**赤いテストから始める**（次節）。これはゲートを
4つに増やす話ではない。機械ゲートの中で「赤の記録があるか」を1項目見るだけで、
判定は既存の3つのまま。

> 実装したモデルは自分の宿題を採点するには優しすぎる。だから機械ゲートと
> 別エージェントで検証する。ループのボトルネックはモデルではなく検証器。

### なぜ3つ目が要るか

**1と2はどちらも出力を見ていない。** テストは実装が持つ内部の性質しか見ず、
レビュアーはコードしか読まない。両方が緑でも、成果物が用をなさないことがある。

実測（このテンプレートで作った色覚検査アプリ）: 10周・約150万トークンかけて全ゲート緑のまま、
**検査プレートの数字が読めないもの**ができた。完了条件は「ドットが重ならない」
「円内に収まる」「該当型で色差が縮退する」で、すべて満たしていた。色彩工学の変換行列が
論文と小数第5位まで一致するかまで検証していた。しかし**「数字が読める」という条件が
どこにも書かれていなかった**。色差を計算しても、図が数字の形をしているかは分からない。
完成後に人が画像を見て初めて発覚した。

**テストで表現しにくい性質は、誰かが見るまで壊れたまま残る。**

## 完了条件は外から観測できる形で書く

`backlog.md` のすべてのタスクに **`見て確かめること:`** を1つ以上書く。
**コードを読まずに人が確認できる形**で書くこと。これが出力ゲートの判定基準になる。

| 作るもの | 「見て確かめること」の例 |
| --- | --- |
| 画像・図形の生成 | 生成物をPNGに書き出し、意図した形が判別できる |
| 画面 | 起動して操作し、スクリーンショットで表示崩れが無い |
| API | 実際にリクエストを投げ、レスポンスのJSONが期待の形 |
| スキーマ変更 | アプリが起動し、マイグレーションが適用されている |
| 純粋なロジック | 代表的な入力に対する出力を一覧で出し、目視で妥当 |

書けない場合、そのタスクは**外から見て何も変わらない**ということ。
それ自体が粒度の誤りか、前後のタスクと統合すべき合図。

### 出力ゲートの進め方

1. 実装エージェントに、成果物を `.loop/artifacts/<slug>/` に出力させる
   （レンダリング結果・スクリーンショット・実リクエスト/レスポンスのログなど）
2. **オーケストレータが実際に開いて見る**。画像なら画像として、画面なら起動して
3. `見て確かめること:` を満たさなければ実装に差し戻す。満たせば記録へ進む
4. 見た結果を `done.md` に1行残す（次の周が「見たのか見ていないのか」を判別できるように）

`.loop/artifacts/` は `.gitignore` に入れる。成果物そのものはリポジトリに残さず、
**見たという事実と結論**だけを `done.md` に残す。

## 縦断を先に通す

**最初の数周で、雑でもいいから端から端まで動く経路を作る。** 層ごとに積み上げない。

前掲の色覚検査アプリでは、計画に「縦断1本を薄く通す」と書いていたのに、実際は
バックエンドを4周積んでから UI に入った。周2の時点で雑な画面があれば、
プレートの不具合は8周早く見つかっていた。

- 縦断が通るまでは、各層を**最小限**にする（見た目・エラー処理・網羅性は後回し）
- 縦断が通ってから、周を重ねて厚くする
- バックログの順序がこれに反していたら、**着手前に並べ替える**

## 差し戻し上限

各ゲートで**3回**まで差し戻す。超えたら **blocked** として扱う。

- **ブランチごと捨てる**（作りかけのコードは残さない）
- `backlog.md` の該当タスクに `blocked:` 行を追記して戻す
- 次のタスクには進まず、**ループを止めて人に報告する**

同じ壁に何度もぶつけてトークンを溶かすより、止まって理由を残すほうが安い。

3回落ちたコードを残しても、次の周は文脈を失った状態でそれを読み解くところから始まる。
ゼロから作り直したほうが速い。**残すのはコードではなく `blocked:` の理由**。

## 赤を先に見る（TDD）

**このテンプレートで最も多い差し戻し理由**は、実装のバグではなく
**テストが実装に対して同語反復になっていて、何も守っていなかった**ことだった。
機械ゲートは緑、レビューも読むだけでは気付けず、verifier が実際に壊してみて発覚する。

実測（このテンプレートで作った1アプリ・全10周）:

| | |
| --- | --- |
| 差し戻し | 10回。うち **8回**がこの型 |
| 差し戻しに伴う追加コスト | サブエージェント消費の **59%**（865,568 / 1,465,239 トークン） |
| 自己検証を規約に入れた直後の周 | 差し戻し **0回** |

**緑は「テストが通った」証拠であって「テストが機能している」証拠ではない。**

実際に起きた形:

| 形 | 何が起きたか |
| --- | --- |
| 空集合への assert | `assertFalse(list.any{...})` が、list が空でも成功していた |
| 期待値を実装から取る | `assertEquals(Registry.require(x), actual)` は誤登録に追従して常に一致する |
| モックの戻り値を検証 | Service をモックしたうえで、テスト自身に直書きした文字列を assert していた |
| 検出力のある assert を消す | 重複整理でループ化した際、唯一のアンカーだったハードコードを消していた |
| 消費が変わらない乱数 | 実装を壊しても RNG の消費数が同じで、出力が偶然一致していた |

**上の3つ（空集合・期待値の逆流・モックの戻り値）は、実装より先に書いていれば書けない。**
どれも「実装を見ながら書いた」ことが原因で、実装が無い時点では成立しないからだ。
だから対策は検査ではなく**順序**にする。

残り2つは順序では防げない。**アンカーを消す**のは緑になったあとの整理で起き、
**乱数の偶然**は赤を見ても分からない。この2つには従来どおりミューテーション試験を残す
（後述「ミューテーション自己検証は『残り』に絞る」）。

### 実装スライスは赤から始める

1. 分解でテストリストを作る（オーケストレータの仕事。`見て確かめること:` を実行可能なテストへ翻訳）
2. リストから**1件**選び、テストを書いて走らせ、**赤を見る**
3. 赤を消す**最小限**の実装を書き、緑にする
4. 緑を保ったままリファクタする
5. リストが尽きるまで2へ戻る

**コンパイルエラーは赤に数えない。** シグネチャだけ先に置き（Kotlin は `TODO()`、
TS は `throw new Error('not implemented')`）、**assertion が落ちる形**で赤にする。
存在しないクラスを呼んで落ちただけでは、そのテストが何を守るか分かっていない。

回し方の詳細・スタック別の書き方・TDDを適用しない対象は `.claude/skills/tdd/SKILL.md`。

### 赤は自己申告させない。コミットで残す

**テストだけのコミットを、実装コミットの前に置く。**

```
test: <対象> — red (<落ちたテスト名>)     ← テストファイル + 未実装スタブのみ
feat: <対象> — green                      ← 実装
```

- 赤コミットは**畳まない**（`--amend` も squash もしない）。1周の枝に残す
- `code-reviewer` は履歴を見て、**赤コミットの時点を複製の上でチェックアウトし、
  本当に赤かったかを再現する**。順序を偽装しても実行で落ちる
- 機械的な順序チェックは `./.claude/hooks/check-conventions.sh` が見る
  （実装ファイルの変更があるのに、先行する test-only コミットが無ければ NG）

### ミューテーション自己検証は「残り」に絞る

赤の記録があるテストは、ミューテーション試験を**省略してよい**。実装が丸ごと無い状態で
落ちているほうが強い証拠で、しかも壊して戻す往復が要らないぶん安い。

次の場合だけ、実装エージェントは従来どおりミューテーション試験を行って結果を報告する。

| まだ要る場面 | 赤だけでは足りない理由 |
| --- | --- |
| **既存テストを変更・削除した** | そのテストに赤の記録が無い。整理で唯一の検出アンカーを消した実例がある |
| **赤がコンパイルエラーだけだった** | 実装を経由した証明になっていない |
| **緑にするために期待値のほうを書き換えた** | テストが実装に追従している。同語反復と同じ |
| 乱数・時刻・並行に依存する | 実装を壊しても偶然一致しうる（上表の最終行） |

手順は変わらない。

1. そのテストが守っているはずの実装を、**1箇所だけ**意図的に壊す
   （値を canary 文字列にする／条件を反転する／ハンドラを消す／フィールドを足す）
2. `./gradlew test --rerun-tasks` を実行し、**どのテストが落ちたか**を記録する
3. 壊した箇所を元に戻し、`git diff` に残骸が無いことと、緑に戻ることを確認する
4. **落ちたテスト名を報告に書く**。落ちなかった場合は、赤くなるまでテストを強化してから返す

呼び出し側（オーケストレータ）は、**赤の記録もミューテーションの報告も無い実装を
verifier に回さない**。

### 検証のコストは実装より安い

3回の差し戻しは、1回のミューテーション試験より高い。そしてミューテーション試験は、
最初から赤を見ておくより高い。**同じ証明を、いちばん安い時点で買う。**

## コメントは実装より高くつく

差し戻しのうち2件は、コードではなく**コメントが事実と食い違っていた**ことが原因だった。

- 「`ex.message` は載せない」と書いた10行下で、最も広い例外型に対して素通ししていた
- 「基底クラスでは body は常に null」と書いてあったが、実測では ProblemDetail を
  先詰めするハンドラが6つあり、コメントが誤った実装を正当化していた

文脈を持たない次の周は、コメントを**前提として信じる**。断定的なコメント
（「〜はできない」「〜は常に〜」「〜経由でしか来ない」）を書くときは、その場で確かめる。
確かめていないなら断定しない。**間違ったコメントは、間違った実装より寿命が長い**。

## ゲートを信じる前に確かめること

| 落とし穴 | 症状 | 対処 |
| --- | --- | --- |
| Gradle の UP-TO-DATE | `make test` が緑でも、実際にはテストを実行していない | 判断に使うときは `./gradlew test --rerun-tasks` |
| `make backend` の短絡 | health が応答する限り再起動せず、**古いコードのまま**動き続ける | `make restart`、または `make stop && make backend` |
| `make test` は DB を起動しない | `ddl-auto: validate` のカラムのズレを**どちらのゲートも検出できない** | スキーマを触る周は実機起動まで人／オーケストレータが確認する |
| Bash の作業ディレクトリ | 前の `cd` が残り、別ディレクトリで `make` が走る | 常に絶対パスで実行する |
| コンパイルエラーを赤と読む | テストが「落ちた」が、実装を経由した証明にはなっていない | シグネチャを先に置き、assertion で落とす |
| 赤コミットを畳む | `--amend` / squash で順序の証拠が消え、verifier が再現できない | 赤コミットは残したまま merge する |

## モデル配分

1周のなかで**難しさは一様ではない**。難しいのは分解と判断で、実装のキーストロークではない。
同じモデルで全部やるとどちらかが必ず割に合わない。**難しいところに強いモデルを置く**。

| 役割 | 誰がやるか | model | なぜ |
| --- | --- | --- | --- |
| 分解・依存の判断・統合・差し戻しの原因特定 | `/work-next` 本体 | **opus** | 1周の質はここで決まる。ここをケチると下流が全部やり直しになる |
| テストリストの作成（何を確かめるか） | `/work-next` 本体 | **opus** | 何を確かめるかは仕様の決定。実装側に決めさせると、実装しやすいものだけがテストになる |
| バックエンド実装（赤→緑→リファクタ） | `backend-dev` | sonnet | 規約と SKILL.md が形を決めている。埋める作業 |
| フロントエンド実装（赤→緑→リファクタ） | `frontend-dev` | sonnet | 同上 |
| 機械的な作業（TODO削除・リネーム・定型テスト・1ファイルの小修正） | 同じ実装エージェント | haiku | 判断が要らない。呼び出し側が `model: haiku` で起動する |
| 設計判断の記録（ADR） | `/work-next` 本体 | **opus** | 判断そのもの。実装エージェントに書かせたら、判断を委譲したのと同じ |
| 合否判定（verifier） | `code-reviewer` | **opus** | 完了条件の片方。ループのボトルネックは検証器であって実装ではない |

本体（オーケストレータ）の model は `.claude/settings.json` の `"model"` で固定する。
サブエージェントの既定は各 `.claude/agents/*.md` の frontmatter。
**上の表は既定値にすぎない。実際に使うモデルはタスクごとに決める**（次節）。

> オーケストレータが自分で実装を書き始めたら、この配分は壊れている。
> opus の仕事は「何を作るか」を決めることで、それを打ち込むことではない。

## タスクごとにモデルを決める

`backlog.md` の `model:` / `review:` で宣言する。省略時は上の既定。

### 選ぶ基準は「難しさ」ではなく「前例の有無」

実測すると、差し戻し回数は実装の難しさとは相関しなかった。効いていたのは次の条件。

**1段上げる**（1つでも該当）

- リポジトリ内に**真似できる既存パターンが無い**（ある層の最初の1周、未知の専門領域）
- **フレームワーク内部の挙動**に依存する（基底クラスの実装を読まないと判断できない）
- 正しさが**単純なアサーションで表現しにくい**
- セキュリティ・データ破損に関わる

**1段下げる**（すべて該当）

- 既存ファイルに**同型のものがあり形をコピーできる**
- 触るファイルが2つ以下
- テストのみの変更、または定型の追加

### 予測せず、外れたら上げる

計画時点でどのタスクが難しいかは当たらない。予測精度を上げるより、外れたときに
自動で上げるほうが確実。

- 差し戻し1回目 → **同じモデル**で再試行（指示の不足であることが多い）
- 差し戻し2回目 → **実装モデルを1段上げる**（haiku → sonnet → opus）
- 3回目 → blocked（現行どおり）

逆に、同種のタスクが下位モデルで連続 PASS しているなら次から下げてよい。
判断材料は `done.md` に残っている。

### verifier は下げずに、呼ぶ範囲を絞る

実測でサブエージェント消費の **51%** が `code-reviewer`（opus）だった。ただし
**ここを単純に下げてはいけない**。実際のバグを見つけていたのは opus の verifier で、
論文由来の実装が別モデルにすり替わって結論の符号が逆になっていた件、
フレームワークの基底クラスが例外ボディを先詰めしていた件（bytecode を読んで
オーケストレータの誤りを覆した）、そして差し戻し10回中8回の同語反復テストは、
いずれも読解と実験の質で見つかっている。

下げる代わりに**範囲を絞る**。

- **2回目以降のレビューは差分限定**。前回のレビューから変わった箇所だけを渡す。
  実測では再レビューが既レビュー済みファイルまで毎回フルで走り、
  2回目以降だけで 444,008 トークンを使っていた
- **赤の再現で足りる範囲は、ミューテーション試験をさせない**。赤コミットを1つ
  チェックアウトして走らせるほうが、壊して戻す往復より安く、証拠としては強い
- **ミューテーションの本数に上限**を置く。変更した公開シグネチャの数に比例させる
- **規約チェックは機械化**して opus に渡さない（package-by-feature、検証アノテーション、
  既存マイグレーションの編集有無、**テストと実装のコミット順**などは機械的に判定できる）

## 権限

無人で回すには事前許可が要る。承認待ちで止まればループにならない。
許可リストは `.claude/settings.json`（設定ファイルには規約を書かない。理由はここに書く）。

許可するのは**1周で必ず通る操作だけ**。次の3つは**意図的に含めない**。

```
git reset --hard   git clean   git branch -D
```

これらが要るのは blocked のときだけで、blocked は元々ループを止めて人に報告する設計。
承認プロンプトが出る瞬間と、人が見るべき瞬間を一致させている。

## 禁止事項

ループは無人で回りうる。次は**どの周でも**やらない。

- `git push` / PR作成 — 外向きの操作は人の判断を待つ
- 既存の Flyway `V__` ファイルの編集 — 新しいバージョンを足す
- `docker compose down -v` — Postgresコンテナは他アプリと共有（CLAUDE.md 設計原則8）
- `backlog.md` に無い作業への横道 — 気づいたことは backlog に**足すだけ**にして、その周では着手しない
- **実装を書いてからテストを後付けする** — 赤を見ていないテストは「書いた」に含めない
  （「赤を先に見る（TDD）」。対象外の判断基準は `.claude/skills/tdd/SKILL.md`）
- `.env` のコミット

## 設計判断の記録（ADR）

ループは文脈をリセットしながら回る。判断の理由が残っていないと、次の周は
コードから逆算できずに**平気で覆す**。`code-reviewer` も根拠が無ければ止められない。
だから判断は `docs/adr/` に残す。規約は `.claude/skills/adr/SKILL.md`。

| 記録 | 何を持つか |
| --- | --- |
| `.claude/skills/` | **どうやるか**。いま従うべき結論 |
| `backlog.md` | **何をするか** |
| `done.md` | **何が終わったか** |
| `docs/adr/` | **なぜそう決めたか**。文脈・代替案・受け入れたコスト |

- **置き場は `docs/adr/`。`.loop/` ではない。** `.loop/` はループの運転状態。
  ADRはアプリの設計に属し、ループを外しても価値が残る。混ぜると `.loop/` の役割が濁る。
- **書くのは `/work-next` 本体（opus）**。実装エージェントに委譲しない（「モデル配分」）。
- **ADRは枝の上に置く**。`.loop/` の更新が base 上なのと逆。理由は2つ。
  verifier のレビュー対象に入れたいこと。そして blocked で枝ごと捨てられたら
  消えてよいこと ＝ **採用されなかった判断は決定ではない**（止まった理由は `blocked:` に残る）。
- **`status` は `accepted` から始める**。ループでは分解と実装が同じ周で確定するので
  `proposed` の期間が無い。人が `/adr` を手で叩くときだけ `proposed` を使う。
- **ADRは新しいゲートを増やさない**。既存のゲート数（機械ゲート・レビュー合否・出力ゲート）は
  出力ゲートと同じ理由では増えない。ADRは「レビュー合否」の中で `code-reviewer` の
  チェック観点として1項目乗るだけ。
- **ADRのBlockerは実装に差し戻さない**。verifier が「ADRが無い」を返したら、
  オーケストレータが**自分で書いてから**機械ゲートに戻る。実装後に判断が判明する周は普通にあり、
  ここで差し戻すと sonnet に判断を書かせることになる。
  ただしこの往復も**差し戻し上限3回に数える**（別枠にすると同じ指摘で無限に回る）。
- **`/find-work` はADRを拾わない**。仕事の源泉は下の2経路のまま。

> 起票の基準は**狭く**取る。命名や規約どおりの実装までADRを求めると、
> `code-reviewer` が誤爆して差し戻し上限3回を溶かす。ADRが増えすぎれば誰も読まなくなる。

## 仕事の源泉

`backlog.md` に仕事が入る経路は2つ。

| 経路 | 何が入るか |
| --- | --- |
| 人が書く | 新機能・仕様変更。**新規開発はこちらだけ** |
| `/find-work` | `make test` の失敗と、コード内の `TODO` / `FIXME`。既存の不備の回収 |
| verifier の Warning | 下の基準を満たすものだけ |

`/find-work` が Automations（仕事の自動発見）にあたる。ただし拾えるのは
**既にある不備**だけで、新機能は拾えない。ここを混同しない。

`/find-work` は**重複を積まない**責任を持つ。同じ失敗テストや同じTODOが
毎回タスク化されると、バックログは消化速度を超えて膨らむ。

### verifier の Warning は全部を起票しない

**起票するのは次のどれかに当たるものだけ。**

- 正しさが壊れる（誤った結果を返す、データが壊れる）
- 情報漏洩・セキュリティ
- 次の周が確実に踏む（依存する周が既にバックログにある）

それ以外は **`done.md` に1行残すだけ**にする。実測では、verifier の Warning から
3周で9件が起票され、機能タスクの前に整理タスクが6件積まれた。人が並べ替えを
指示するまで、ループは整理ばかりを進めていた。最終的に、起票された整理タスクの
多くは作られないまま凍結された。

### 機能を整理タスクで追い越さない

`backlog.md` は上から取るので、**整理タスクを機能タスクの前に置かない**。

- 新しい整理タスクは、**未着手の機能タスクの後ろ**に積む
- 整理タスクだけを連続で取らない。機能が残っているなら機能を優先する
- 例外は、その整理をしないと次の機能が作れない場合（依存があるなら機能扱い）

## backlog.md の書式

```markdown
- [ ] <タスク名（1行で何を作るか）>
      db: postgres | dynamo | none
      model: haiku | sonnet | opus      <実装に使うモデル。省略時 sonnet>
      review: sonnet | opus             <verifier に使うモデル。省略時 opus>
      adr: required | none              <設計判断を含むと人が判断した場合。省略時はループが判定>
      tdd: n/a <理由>                   <設定・配線のみでテストを先に書けない場合だけ。省略時は必須>
      見て確かめること: <コードを読まずに人が確認できる受け入れ条件。必須>
      完了条件: <既定の3ゲートに追加される受け入れ条件>
      source: <どこから来た仕事か。/find-work が付ける>
      blocked: <なぜ止まったか。ループが付ける>
```

- **`見て確かめること:` は省略不可**。出力ゲートの判定基準になる。
  書けないタスクは粒度が誤っている（上の「完了条件は外から観測できる形で書く」を参照）
- `model:` / `review:` — 選び方は「タスクごとにモデルを決める」を参照。
  **差し戻し2回目でループが `model:` を1段上げる**（上げた事実は `done.md` に残す）
- `adr:` — 人が「これは設計判断を含む」と先に宣言する行。省略時はループが要否を判定する
- `tdd:` — **省略が既定**（＝赤から始める）。`n/a` を書けるのは
  `.claude/skills/tdd/SKILL.md`「TDDを適用しないもの」に当たる場合だけ。
  理由を書かない `n/a` は無効として扱い、ループは通常どおり赤から始める
- `見て確かめること:` は分解時に**テストリスト**へ翻訳される。翻訳できないなら、
  それは出力ゲートでしか確かめられない性質（見た目・実機起動）である合図
- その他の属性行は省略可。省略時は `db: none`、既定ゲートのみ、出所は人
- `source:` — `/find-work` が重複判定に使う。**人もループも書き換えない**
- `blocked:` — 付いている行はループが**飛ばす**。人が原因を解いてから消す

## done.md の書式

```markdown
## YYYY-MM-DD <タスク名>
- branch: loop/<slug>
- 変更: <主要ファイル>
- ゲート: make test && make build ✅ / code-reviewer PASS
- 赤: <赤コミットのハッシュ> <落ちたテスト名>  <TDD対象外だった場合は「対象外: 理由」>
- adr: docs/adr/NNNN-<kebab>.md  <起票した場合のみ。ブランチのslugとは別物>
- メモ: <次の周が知っておくべきこと。無ければ省略>
```

## 人が見るべきところ

ループは速度を上げるが、**理解を代わりに育ててはくれない**。

- `done.md` が伸びているのに中身を読んでいない → 理解のギャップが開いている合図
- 同じ `blocked:` が繰り返し出る → 規約かスキル側の記述が足りていない。ループでなく `.claude/skills/` を直す
