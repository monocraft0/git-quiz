# TDD（赤を先に見る）

このリポジトリの実装は**テストから始める**。実装コードを書く前に、
**落ちるテストを実際に走らせて赤を見る**。順序は規約であって好みではない。

## なぜ順序を規約にするか

このループの差し戻し10回のうち **8回**は実装のバグではなく、
**テストが同語反復で何も守っていなかった**ことだった（`.loop/LOOP.md`
「赤を先に見る（TDD）」）。
対策として実装後の**ミューテーション自己検証**（実装を1箇所壊して赤を確認）を義務づけたが、
これは**事後に証明を買っている**。壊して、走らせて、戻す往復ぶんだけ高い。

**実装より先に書いたテストは、赤を見た時点で同じ性質を無料で手に入れている。**
実装が無い状態で落ちたのだから、そのテストは少なくとも実装を経由している。
空集合への assert も、モックの戻り値を検証するだけのテストも、期待値を実装から取るテストも、
**実装が存在しない時点では書けない**。だから順序が検出力を作る。

順序で防げないものもある（緑のあとの整理で検出アンカーを消す、乱数で偶然一致する）。
そこには下の「ミューテーション自己検証がまだ要る場面」が残る。

| | 実装後に書くテスト | 実装前に書くテスト |
| --- | --- | --- |
| 検出力の証明 | ミューテーション試験が要る（壊す→走らせる→戻す） | 赤を見た事実がそのまま証明 |
| 同語反復 | 実装を見ながら書くので起きる | 実装が無いので起こしようがない |
| 仕様の置き場 | 実装が仕様になる | テストが仕様になる |

## サイクル

```
テストリストを作る（何を確かめるかを列挙）
  ↓
1件選ぶ  ← 1度に赤くするのは1つだけ
  ↓
赤     テストを書き、走らせて落ちるのを見る（コンパイルは通っていること）
  ↓
緑     赤を消す最小限の実装を書く。走らせて緑を見る
  ↓
リファクタ  緑を保ったまま整える（テストは変えない）
  ↓
次の1件へ。リストが尽きたらスライス完了
```

## 赤の質（ここが本体）

**コンパイルエラーは赤ではない。** 存在しないクラスを呼んで落ちても、
そのテストが何を守るかは何も分かっていない。証明になるのは
**コンパイルが通ったうえで assertion が落ちること**。

そのために、**シグネチャだけ先に置く**。中身は未実装のまま赤にする。

```kotlin
// backend: 中身は TODO() のまま。呼べるが答えは返さない
fun summarize(id: Long): SummaryResponse = TODO("not implemented")
```

```ts
// frontend: 型は確定させ、実体は未実装
export function useSummary(id: number): SummaryState {
  throw new Error('not implemented');
}
```

赤を見たら、**落ちた理由を読む**。

| 落ち方 | 意味 | どうするか |
| --- | --- | --- |
| assertion failure（期待値と実際が両方出る） | 正しい赤 | 緑に進む |
| コンパイルエラー / import 解決失敗 | 赤に数えない | シグネチャを置いてから書き直す |
| `NotImplementedError` / `not implemented` | 正しい赤 | 緑に進む |
| 別のテストまで一緒に落ちた | スライスが広すぎる | 1件に絞る |
| そもそも緑になった | **そのテストは何も守っていない** | 実装を経由する assert に書き直す |

**最後の行が一番重要**。実装が無いのに緑になるテストは、書いた時点で無価値だと分かる。
これが実装後に書いていたら、ミューテーション試験まで気付けなかった。

## 赤は証拠として残す

自己申告は検証できない。**赤いテストを単独のコミットとして枝に残す。**

```bash
git add <テストファイルだけ>
git commit -m "test: <対象> — red (<落ちたテスト名>)"
# ここから実装
git add -A && git commit -m "feat: <対象> — green"
```

- テストコミットには**実装ファイルを含めない**。混ぜた瞬間に順序が証明できなくなる。
  シグネチャのスタブ（`TODO()` / `throw`）だけは実装ファイルに要るので、
  **スタブは赤コミットに含めてよい**（中身が無いことがコミットの diff で見える）。
- コミットメッセージに**落ちたテスト名**を入れる。あとから追う唯一の手がかり。
- **赤コミットは畳まない**（`--amend` も squash もしない）。これが verifier とレビューの入口。
- 1スライスに赤コミットが複数あってよい。テストリストの件数だけ赤があるのが自然。

`code-reviewer` はこの履歴を見て、**赤コミットの時点をチェックアウトしてテストを走らせ、
本当に赤かったかを再現する**。順序が偽装されていればそこで落ちる。

## テストリストの作り方

実装に入る前に、**何を確かめるかを列挙**する。オーケストレータが分解時に作り、
実装エージェントに渡す（`.loop/LOOP.md`「モデル配分」）。

タスクの `見て確かめること:` を、**実行できるテスト**へ翻訳したものがテストリスト。

| `見て確かめること:` | テストリストへの翻訳 |
| --- | --- |
| 一覧APIが空のとき `[]` を返す | `GET /api/todos` が 200 と空配列（サービスが空を返す場合） |
| 名前が空のPOSTは400 | `@field:NotBlank` 違反で 400、`message` にフィールド名 |
| 一覧が空のとき「まだありません」と出る | 空配列を返すモックで `getByText('まだありません')` |

書き方の目安:

- **正常系1本**から始める。縦断が通る最短の1本を最初に赤くする
- 次に**境界**（空 / 0件 / 上限）、次に**失敗系**（検証エラー / 404 / 通信失敗）
- 1件は**1つの振る舞い**。1テストで3つ確かめたくなったら3件に割る
- リストは実装中に増えてよい。思いついた確認は**リストに足すだけ**にして、
  いま赤くしている1件を先に緑にする

## TDDを適用しないもの

順序を全部に強要すると空回りする。**次は対象外**。

| 対象外 | なぜ |
| --- | --- |
| 設定・配線（`application.yml` / `docker-compose.yml` / Makefile / `.claude/` / ドキュメント） | 振る舞いの単体テストが存在しない。確認は起動と出力ゲート |
| Flyway マイグレーションの適用そのもの | `make test` はDBを起動しない。実機起動でしか出ない（`.loop/LOOP.md`） |
| 見た目・レイアウトだけの変更 | テストで固定すると壊れやすいだけで何も守らない。出力ゲートで見る |
| 振る舞いを変えないリファクタ | 新しい赤は要らない。**既存の緑を保つことが条件**。テストを一緒に書き換えたら、それはリファクタではない |

対象外のものを扱う周は、**その旨を報告に1行書く**（「テストを先に書かなかった理由」）。
黙って飛ばすと、TDDを守った周と区別が付かなくなる。

## ミューテーション自己検証がまだ要る場面

赤の記録があれば、そのテストのミューテーション試験は**省略してよい**。
赤はミューテーションより強い証拠（実装が丸ごと無い状態で落ちている）で、しかも安い。

ただし次の場合は**引き続き必須**。

| 場面 | なぜ赤だけでは足りないか |
| --- | --- |
| **既存テストを変更・削除した** | そのテストに赤の記録が無い。整理の過程で唯一の検出アンカーを消した実例がある |
| **赤がコンパイルエラーだけだった** | 実装を経由した証明になっていない |
| **緑にするために期待値のほうを書き換えた** | テストが実装に追従している。同語反復と同じ |
| 乱数・時刻・並行に依存するテスト | 実装を壊しても偶然一致しうる（`.loop/LOOP.md` の実例） |

手順は `.loop/LOOP.md`「ミューテーション自己検証」と同じ。

## バグ修正は「再現する赤」から

不具合の修正は**まず落ちるテストで再現する**。直してから書いたテストは、
その不具合を二度と捕まえない形で書かれがち。

`/find-work` が積んだ「失敗しているテスト」のタスクは、**赤が既に存在する**。
新しく赤を作る必要は無く、そのテスト名を赤の記録として報告すればよい。
