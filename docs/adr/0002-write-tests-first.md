## 文脈

このテンプレートで最も多い差し戻し理由は、実装のバグではなく
**テストが同語反復で何も守っていなかった**ことだった。

実測（このテンプレートで作った1アプリ・全10周）:

| | |
| --- | --- |
| 差し戻し | 10回。うち **8回**がこの型 |
| 差し戻しに伴う追加コスト | サブエージェント消費の **59%**（865,568 / 1,465,239 トークン） |
| `code-reviewer`（verifier / opus）の消費 | サブエージェント消費の **51%** |

対策として `.loop/LOOP.md` に**ミューテーション自己検証**（実装を1箇所壊して赤を確認する）を
義務づけ、直後の周は差し戻し0回になった。効いてはいる。ただしこれは
**事後に証明を買っている**。壊して、走らせて、戻す往復ぶんだけ高く、
verifier 側でも同じ試験を再現するのでコストが二重に乗る。

原因をさかのぼると、規約が**順序を定めていなかった**ことに行き着く。
これまでの設計原則6は「変更には必ずテストを添える」で、いつ書くかを言っていない。
結果として既定の手つきは「実装 → テスト」になり、**実装を見ながらテストを書く**ことになる。
空集合への assert も、モックの戻り値の検証も、期待値を実装から取る書き方も、
すべて実装が目の前にあるから書ける。**実装が存在しない時点では書けない。**

## 決定

**実装より先に落ちるテストを書き、赤を実際に見てから実装する（TDD）**を、
全アプリ共通の設計原則にする。赤は自己申告させず、**テストだけのコミット**
（`test: <対象> — red (<落ちたテスト名>)`）を実装コミットの前に置いて枝に残す。

- 何を赤と認めるかの基準・回し方・適用外は `.claude/skills/tdd/SKILL.md` に置く。
  **コンパイルエラーは赤に数えない**（シグネチャのスタブを先に置き、assertion で落とす）
- `code-reviewer` は履歴を見て、**複製の上で赤コミットをチェックアウトして再現する**
- 順序の機械チェック（`test:` コミットが先行しているか）は
  `.claude/hooks/check-conventions.sh` に入れ、opus に grep で分かることをさせない
- **正しい赤があるテストは、ミューテーション試験を省略する**。
  試験は「既存テストの変更・削除」「赤がコンパイルエラーだけ」「期待値を書き換えた」
  「乱数・時刻依存」に限定する
- ゲートは増やさない。判定は従来どおり機械ゲート / レビュー合否 / 出力ゲートの3つで、
  赤の記録は**機械ゲートの中の1項目**（着手条件）として見る

## 結果

### よくなること

- 同語反復テストが**書けなくなる**。検査で見つける問題から、順序で起こらない問題に変わる
- 同じ証明をいちばん安い時点で買える。赤 < ミューテーション自己検証 < 差し戻し3回
- verifier の仕事が減る。赤を再現した範囲は試験を省けるので、消費51%の内訳が軽くなる
- テストが仕様の置き場になる。`見て確かめること:` → テストリスト → 実装、と
  「何を作るか」が実装の前に一度言語化される
- 順序が**履歴に残る**ので、次の周も人も後から検証できる。done.md の `赤:` 行で追える

### 悪くなること

- 1スライスあたりのコミット数が増える（赤と緑で最低2つ）。枝の履歴は長くなり、
  squash できない（畳むと証拠が消えるため）
- スタブ（`TODO()` / `throw`）を先に置く手数が毎回かかる。置き忘れると
  コンパイルエラーになり、それは赤として認められないので書き直しになる
- 適用外の線引きが必要になった（設定・配線・見た目・リファクタ）。ここが緩いと
  `code-reviewer` が誤爆し、ADRと同じく差し戻し上限3回を溶かす。
  `tdd: n/a <理由>` という逃げ道を用意したぶん、宣言が濫用されていないかを人が見る責任が残る
- 探索的な実装（何を作るか自体が固まっていない周）とは相性が悪い。
  テストリストが作れないタスクは、粒度か順序が間違っている合図として扱うことにした

## 検討した代替案

- **ミューテーション自己検証だけを続ける** — 効果は実証済みだが事後の証明で、
  実装エージェントと verifier の両方で払う。順序を変えれば新規テストぶんは無料になる
- **TDDを「推奨」に留める（強制しない）** — 推奨は守られない。既定の手つきは
  「実装 → テスト」のままになり、いまと何も変わらない。順序は**規約か、無いか**のどちらか
- **カバレッジ閾値を機械ゲートに足す** — 同語反復テストはカバレッジを上げる。
  8回の差し戻しはどれもカバレッジでは検出できなかった
- **verifier の判定を厳しくする** — 既に「迷ったら Blocker」で運用しており、
  それでも読むだけでは気付けなかった（実際に壊してみて発覚している）。
  検証器を強くするほどループのボトルネックが太る
- **赤の記録を報告文だけで受け取る（コミットを分けない）** — 自己申告は検証できない。
  実際、ミューテーション試験の報告を都合よく読み違えた実例がある
  （モックのスタブ不足で落ちただけを「検出できている」と読んだ）
